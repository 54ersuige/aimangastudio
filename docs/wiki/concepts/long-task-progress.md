# 「生成话目没反应」的真相：它转了 8 分钟

> 用户 2026-10-16 下午的原话：**「生成话的时候，没有反应啊」**

## 排查路径（每一步都排除了一个常见猜测）

| 猜测 | 验证方式 | 结果 |
|---|---|---|
| 服务挂了 | `/health` | ✅ 正常 |
| 任务卡在队列 | `/api/tasks` | ✅ 空 |
| 前端没点到 | `generations.jsonl` | ❌ **请求日志 3 条，请求确实到了后端** |
| 模型/供应商挂了 | 直连 `/chat/completions` | ✅ 1 秒返回 |
| prompt 写错了 | dump 完整 prompt | ✅ 1935 字，比成功的那几次还短 |

**第一个真正的线索**是日志的 kind 统计：

```
arc-chapters        33 次请求
arc-chapters-response 27 次响应   ← 差 6
```

响应是**独立一条**日志。用户那三次只有请求、没有响应 → 模型调用没返回。
（同一份文件里 `replan-chapter` 是 6:6 配对的，说明日志机制本身没问题。）

## 完整时间线（真相在这里）

```
16:13:33  用户第一次点
16:19:25  第 1 次尝试返回，但字数不够（371/368/353/346 < 要求 360）→ 整轮重写
16:21:40  第 2 次成功，4 话生成完毕
```

**它一直在跑，8 分钟。只是界面上只有一个不会动的「生成中…」。**
用户 16:15 又点了一次，那次撞上 409「该季已有 chapter」——
于是 8 分钟的正常等待被误判成故障，又制造了一个真故障。

## 为什么这么慢

推理型模型（M3）的输出里 **84% 是思考 token**：

```
总输出 21143 字符，其中思考 17783 字符（84%）
思考里出现：「不对」2 次、「再看一下」2 次、「重新」5 次
```

它在纠结一个真实的措辞歧义：`把季"新人"…拆分成话目`
——「新人」到底是季的标题还是这一话的内容？

而 `callStructuredJson` **根本没设 maxTokens**（provider 只在
`req.maxTokens !== undefined` 时才传），所以完全由模型自行决定思考多久。
批量出 4 话 = 4 倍思考量。

## 根因有两个，第二个更阴险

### 根因 1：长任务没有进度反馈

出图有进度条，**生成话目完全没有**。按钮只有一句「生成中…」，
8 分钟不动和真卡死长得一模一样 —— 界面在用户眼里无法区分这两件事。

### 根因 2：text 模型超时 240s，而批量出 4 话实测要 5~8 分钟 ⭐

改完 task 队列后我实测跑了一次，结果：

```
[16:30:37] 发起
[16:34:40] status=error  ERROR: 请求超时（240s 内未返回）
```

**任务在 4 分钟处被掐断了。** `runtime-config.json` 里 `text.timeout = 240000`。

这条比根因 1 更危险，因为：

- 模型跑得快时它能过去 —— **属于「运气好的时候看起来没问题」**
- 你 16:13 那次能成功，是模型恰好在 240s 内跑完了两轮
- 它极易被改回去，而且改回去之后没有任何测试会红

## 为什么这么慢

推理型模型（M3）的输出里 **84% 是思考 token**：

```
总输出 21143 字符，其中思考 17783 字符（84%）
思考里出现：「不对」2 次、「再看一下」2 次、「重新」5 次
```

它在纠结一个真实的措辞歧义：`把季"新人"…拆分成话目`
——「新人」到底是季的标题还是这一话的内容？

而 `callStructuredJson` **从未设 maxTokens**（provider 只在
`req.maxTokens !== undefined` 时才传），所以思考时长完全由模型自行决定。
批量出 4 话 = 4 倍思考量。

## 修法

1. **三个端点改走 task 队列**（`runTask`），立刻返回 `taskId`，
   前端轮询而不是挂着一条 HTTP 连接等 8 分钟：
   `generate-chapters` / `append-next-chapter` / `replan`
2. **`callStructuredJson` 新增 `onProgress`**，
   每次尝试上报「第几次 / 共几次 / 什么阶段」。
   0-49% 给首轮、50-99% 给重写，让进度条真的在动，
   并且**让「正在重写」这件事本身可见**——那是用户最容易误判为卡死的时刻。
3. **`callStructuredJson` 新增 `timeoutMs` per-call 覆盖**，
   并**按每次尝试单独放宽**：

   ```ts
   const perAttemptMs = opts.timeoutMs ?? 360000;
   const attemptConfig = { ...config, timeout: perAttemptMs };
   ```

   > 第 2 次重试不能沿用第 1 次消耗过的墙钟时间 ——
   > 否则「每次尝试 6 分钟」实际只有第一轮有 6 分钟。

   三个端点分别给 480s / 300s / 300s。

   **刻意不全局抬高 timeout**：那会让所有短任务（角色生成、世界观）
   失败时也干等 10 分钟才报错。**只有确定很慢的调用才覆盖。**

### 坑：我造了覆盖对象，却没传进去 ⭐

改完第一次实测 —— **还是 240s 超时**。查了半天配置、schema、provider 都没问题。

真因只有一行：

```ts
const attemptConfig = { ...config, timeout: perAttemptMs };  // ← 造好了
const provider = getTextProvider(attemptConfig);
...
const result = await provider.generateText(config, req);     // ← 传的却是 config
```

**这段 bug 极其阴险**：测试全绿（`timeoutMs`、`perAttemptMs`、`attemptConfig`
这些字符串都存在），代码读起来也"像是实现了"，但超时一点没变。

补的测试不是断言「覆盖对象存在」，而是断言**它被用上了**：

```ts
for (const site of HELPERS.match(/provider\.generateText\(\s*\w+\s*,/g) || []) {
  expect(site).toContain('attemptConfig');
}
expect(HELPERS).not.toMatch(/provider\.generateText\(\s*config\s*,/);
```

> **同族**：和我之前在 `dump_prompts` 上踩的坑完全一样 ——
> 「某物不存在」的真实原因常常是「我没在正确的地方看 / 我造了但没用」。
> **断言存在性 ≠ 断言生效性。** 这类 bug 只有端到端真跑一次才会暴露。

4. **重复点击给出人话 409**：「本季正在生成话目，请等它跑完（通常 5~10 分钟）
   ——不用重复点击。」此前返回的是「该季已有 chapter」，
   用户完全看不懂自己为什么被挡。
5. **前端按钮旁加进度条 +「通常 5~10 分钟，请勿重复点击」** ——
   事先告知时长，用户就不会在第 3 分钟失去耐心。

## 实测验证

| 项 | 修复前 | 修复后 |
|---|---|---|
| HTTP 返回 | 8 分钟（挂着等） | **0 秒**（返回 taskId） |
| 超时 | 240s 会中途掐断 | 480s，撑得住实测 5~8 分钟 |
| 进度 | 无 | 可轮询，重试阶段可见 |
| 重复点击 | 409「该季已有 chapter」（看不懂） | 409「正在生成，请等它跑完」（能懂） |

## 教训

**「没反应」是个症状，不是诊断。** 用户说没反应时，先去日志里找
「请求发了没有」「响应回来了没有」这两个事实，而不是先去查服务活没活、
模型通不通 —— 那些都是「它坏了」的猜测，而这个故障里它们全部正常。

**超时值必须按实测耗时定，不能沿用默认。** 240s 这个值在短任务上完全够用，
看起来毫无问题；只有当某类任务真的跑到 5 分钟以上，它才会突然发作。
这类「平时不发作」的缺陷必须配测试锁住，否则一定会被改回去。

另一个同源教训：**返回给人看的错误信息必须能让人看懂下一步做什么。**
「该季已有 chapter」是内部状态描述，
「请等它跑完（约几分钟）——不用重复点击」才是给人看的。
