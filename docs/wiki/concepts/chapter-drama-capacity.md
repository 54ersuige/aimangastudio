# 一话必须有戏剧张力

> 用户 2026-10-16 的原话：
> **「每一话都要有一些戏剧张力啊，这样才好，要改的。」**
> 更早的一条纠正同样关键：**「我说错了，是一话一天。」**

## 先把发布模型说对

之前的理解错了：一直以为 page（批次）是发布单位。
用户澄清是 **一话 = 一天 = 一条长图 = 一次发布**。

这一句改写了一切。「每话 12-18 格」因此不是体量审美指标，
而是 **「这一话够不够演完一件有戏剧张力的事」**。
一格就是一个画面点，6 格是最低可演出的动作序列，12-18 格才有转折的余地。

## 病根（真实数据，不是推断）

《加油啊》现有 4 话，summary 字数与 pageCount：

| 话 | summary 字数 | pageCount | 声明容量 | 实际够几拍 |
|---|---|---|---|---|
| 报到 | 104 | 3 | 18 格 | **5 拍** |
| 加班 | 104 | 3 | 18 格 | 5 拍 |
| 哈哈 | 102 | 3 | 18 格 | 5 拍 |
| 十一点 | 101 | 3 | 18 格 | 5 拍 |

决定性的一条：**《报到》的 6 格与 summary 里的 6 句话一一对应，一格不差。**

```
报到 → 电梯玻璃倒影 → 前台递工牌 → 看见靠窗工位 → 周敏扫一眼 → 坐下
```

也就是说 summary 的信息量**只够撑 1 批（6 格）**，容量却预留了 3 批。
剩下 12 格是没有剧情可写的空批次 —— 4 个话全部如此。

## 界面在把「还没填」误报成「不够」

进度显示把「已填 6 格」当成「只规划了 6 格」，于是给出：

> 本话规划 3 批（6 格），低于每话目标 12-18 格 —— 剧情没讲完就点续写

这句话把用户往硬编内容的坑里推：为了凑格数去注水，
而 [[review-thresholds-relaxed]] 刚刚才把审核门槛调低，两个问题正好互相打架。

## 判据：画面点估计，不是数句子

`server/series-routes/chapter-capacity.ts` 是「一话该有多少内容」的唯一判据，
三个规划入口共用同一个函数与同一段 prompt 约束（`CHAPTER_CAPACITY_RULE`）：

- `CHARS_PER_PANEL = 20` —— 每格约 20 字画面描述
- `PANELS_PER_BATCH = 6`
- `PANELS_PER_EPISODE_MIN / MAX = 12 / 18`

**为什么用字数 ÷ 20 估拍数、而不是数句子：**
模型爱写长句（「周敏扫了一眼，靠窗那个工位空着，像是早就给她留的」），
一句能藏三个画面点。数句子会系统性低估，让真正合格的 summary 被误杀。

撑不起就打回重写，返工指令是**可执行的**，不是「写长一点」：

1. 具体字数目标（这 104 字只够 5 拍，需要 18 格）
2. 必须拆出确切数量的画面点
3. 必须有冲突或转折
4. 结尾停在未解决的地方

## pageCount 的四重不一致（此前目标从未被强制）

| 位置 | 原来的范围 |
|---|---|
| `ChaptersSchema` | 1-12 |
| prompt 告诉模型 | 2-6 |
| append 端点 | 2-8 |
| `UpdateChapterSchema` | 2-8 |

**四个地方四个范围。** 结论是「每话 12-18 格」这个目标在规划阶段
**根本没有被强制过** —— 它只是 UI 上的一句提示文字。
现统一为 2-3（12-18 格），`ChapterListZ.pageCount` 同步。

## 按钮语义：同一个动作此前有三种名字

`拆解分镜` / `续写本话` / `续写本话（追加一批）` —— 后端是同一个动作。

而且**本话全满时按钮仍叫「续写本话」，但会去填下一话的第一批**，
名实不符，用户无从察觉。

现在按「本话还剩几个空批次」给准确文案：

- 本话还有空格 → **「拆解第 N 批」**
- 本话全满 → **「进入下一话」**

## 改动清单

| 文件 | 改动 |
|---|---|
| `server/series-routes/chapter-capacity.ts` | 新建，容量判据唯一来源 |
| `server/series-routes/chapters.ts` | 三处规划入口接入规则 + 校验 |

## 验证

- `npm run check` exit 0 · `npm run build` exit 0
- vitest **117 passed**（新增 15 项容量判据测试）
- 真实数据跑 `capacity-audit`：4 话 **全部被判打回**（104 字 → 够 5 拍 / 需 18 格）

判据会触发，说明它不是摆设。

## known-issue

现有 4 话的 summary 生成于新规则之前，**不会被自动改写**
（自动改写 = 悄悄改掉用户写过的剧情，不可接受）。
要让它们撑满 18 格，需要重新规划或手动扩写 summary。
`tools/capacity-audit.ts` 能指出哪些话需要处理。

# 补记（2026-10-16 下午）：实跑之后又抓出四个问题

上面这一版是**只做了代码审查和静态验证**。真正跑一次之后，
才发现四个静态检查全都看不出来的东西。

## A. prompt 里的字数要求和代码差了整整一倍 ⭐

```
prompt 原文（手写）：pageCount=2 需 ≥120 字，pageCount=3 需 ≥180 字
checkChapterCapacity 实际要求：2 × 6 × 20 = 240 字 / 3 × 6 × 20 = 360 字
```

模型**照着 prompt 写必然被校验打回**，一轮轮返工直到停滞 ——
正好是用户最不想要的「频繁报错、停滞不前」。

更糟的是**测试把这个 bug 一起锁住了**：
`expect(CHAPTER_CAPACITY_RULE).toContain('120')` 是绿的，
因为它断言的正是那个错值。测试通过 ≠ 规则正确。

**修法：规则里的数字全部由常量推导，不许手写。**

```ts
`按每格 ${CHARS_PER_PANEL} 字估算：pageCount=${BATCHES_PER_EPISODE_MIN} 需 ≥${...} 字`
```

并加一条测试断言「rule 里的下界 == 常量算出来的下界」，
外加一条 `not.toContain('需 ≥120 字')` 钉死旧错值。
那条旧断言也一并改成推导值。

## B. pageCount 三处自相矛盾

统一 pageCount 时只改了**规划入口**，漏了三处「总数/范围」的手写字面量：

| 位置 | 原来 | 矛盾在哪 |
|---|---|---|
| `append-next-chapter` | `Math.min(8, pageCount \|\| 4)` | prompt 说「4 个批次」，schema 只允许到 3 |
| `generate-chapters` | `plannedChapterCount * 4` | 每话最多 3 批，**总和永远达不到 4×话数** |
| `UpdateChapterSchema` | `.max(8)` | 手动编辑能设出 48 格容量，没有任何校验管得住 |

第三条尤其说明问题：**「12-18 格」只对 AI 生效、对人不生效。**

模型在互相矛盾的指令里**只会取最松的那条**，于是要么被 schema 拒、
要么输出与 prompt 不符。新增 `feasibleTotalBatches()` 把总数夹进真正可达的区间：

```ts
feasibleTotalBatches(requested, chapterCount?, min, max)
```

`chapterCount` 传 `undefined` 表示「话数由模型决定」，
此时只受全局区间约束 —— 这一点第一版写错了（把「未知」当成「只有 1 话」，
把 12 批压到 3 批），是被自己的测试抓出来的。

## C. 实跑第一版：张力跑偏成「暧昧」

第一次实跑重新规划《报到》：**104 字 → 453 字**，容量校验确实挡住了弱版本。

但**亲自读**之后的问题是另一回事：

- 周敏的靠近 + 林珂那句「周姐对你挺上心」= 办公室言情暗示，不是冲突
- **主角全程被动**：小跑才跟上、手心出汗、塑料壳差点滑掉、站起来
  —— 他从没做过一个选择，也没有任何东西处在风险中
- 18 格 New Yorker 式短篇，没有代价就没有戏剧，只剩下气氛

**结论：容量这一维现在有代码强制，张力这一维还只是一句 prompt。**
只写「必须有冲突或转折」，模型会把「张力」理解成「气氛紧张」。

补充进规则的第 3、4、7 条：

```
3. 主角必须做出至少一个主动的选择或反抗 —— 不能整话都在被动承受、跟着走
   反例（不合格）：他小跑才跟上、手心出汗、被带着走。
4. 必须有一样东西处在风险里，并让他在本话内真的为此付出一点代价。
7. 不要把「张力」写成暧昧/紧张气氛。暧昧不等于冲突。
```

并用测试断言这三条在 rule 里，防止以后被精简掉
（`expect(rule).toContain('主动的选择或反抗')`）。

## D. 没有「重新规划已有话」的入口

三个生成端点**全是新建**。用户唯一能对已有话做的事是手动改字 ——
但「这一话太平了，给我一版有张力的」恰恰是最常出现的诉求。

新增 `POST /series/:id/chapters/:chapterId/replan`，两条不能越过的线：

1. **不静默丢用户已经出好的图。** pageCount 变大就补空批次；
   变小也不删已有批次，而是把 pageCount 抬回实际批次数并如实告知。
2. **老分镜与新剧情不再对应，必须说出来。** 返回 `notes` + `stalePanels`，
   界面明确提示，而不是让用户以为那些图还是照着新剧情画的。

## 顺带：旧图标记

整批重画时，个别格失败会保留它原来的旧图（宁可留旧图也不要留空洞）——
策略是对的，但**「6 格齐全」因此可能是假象**。

真正的代价不是那格图旧，是**用户以为自己看过新版了**。
所以 `Panel` 加 `stale` / `staleReason`，重画路径失败时标记，
成功时清除，界面在角上打「旧图」红标。

## E. 实跑四话后的结论：达成了，但暴露两个新问题

四话全部重跑（62-116s/话），**张力标准 4/4 达成**：

| 话 | 字数 | 拍数 | 主角主动选择 | 代价 | 结尾未解决 |
|---|---|---|---|---|---|
| 报到 | 469 | 23 | 拒绝签第七条 | 不能告诉妈 | 妈妈来电响七声没接 |
| 加班 | 537 | 26 | 拒绝酒吧邀约 | 错过妈妈的排骨 | 手机震了没看 |
| 哈哈 | 830 | 41 | 抓老张机会署名 | 降薪转前台 | 「哈哈，听话就好」 |
| 十一点 | 672 | 33 | 截屏取证找 HR | 妈妈被周敏拿捏 | 连删掉的草稿 IP 都被掌握 |

第 4 话最好：周敏那句「你妈每月那通电话，都在问我你表现怎么样」
把冲突从暧昧彻底变成威胁。

### 新问题 1：判据只卡下限，完全不管上限

拍数 23 / 26 / 41 / 33，需求一律 18 —— 比值 1.28 / 1.44 / 1.83 / 2.28。
「写得越猛越好」，于是画面点塞不进格、或被静默丢弃。

`checkChapterDensity()` 阈值定 **1.5**（照这组实测比值来的，中位约 1.6），
**刻意只提示不拦截** —— 加严就等于把用户重新推进
「频繁报错、停滞不前」，那是他明确要求避免的。

### 新问题 2：套路化才是「可持续张力」的真正威胁

四话全是同一形态：**某人施压 → 主角拒绝 → 代价落在妈妈身上**。
单看每话都有张力，连着看就是同一个模子。读者看穿了就不再紧张。

规则第 8 条要求「本话冲突形态不能和前面几话重复」，
并列出可换的形态（主角先发制人 / 代价落在别人身上 / 误会与真相错位 / 主角赢了但更糟）。

> ⚠ **这条规则写进去了，但未实跑验证。**
> 前 7 条是跑过 4 话确认有效的；第 8、9 条是跑完后才加的，
> 下一话才会用到。不实测就宣称「已修好」正是这轮反复在修的毛病。
