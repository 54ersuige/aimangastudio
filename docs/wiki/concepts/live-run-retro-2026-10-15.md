# 实跑复盘：两个静默失效的 bug

> [[four-gate-fusion]] 上线后的**第一次真实出图**（6 格，并发 3）暴露了两个 bug。
> 两者都不是单测能发现的 —— 它们只在真实 provider + 真实耗时下才显形。

## Bug 1：合一闸 30s 超时，四块全部静默作废

**现象**：6 格里有 2 格四道闸全是 `null`，但出图照样成功（fail-open 生效，用户没察觉）。

**日志证据**：
```
{"kind":"panel-gate-error","model":"agnes-3.0-flash","error":"请求超时（30s 内未返回）"}
```

**根因不是代码默认**。`server/config.ts` 里 vision.timeout 的默认值是 **90000**，
但 `server/runtime-config.json` 存的是 **30000** —— 被更早的配置盖住了。

**为什么之前没炸**：合并前是 4 个各自很轻的调用（肢体/性别/对齐各 1 张图 8000 tokens，
评审 5 张图 16000），每个都能塞进 30s。合并后一次调用要吃 5 张图 + 4 块输出 + 20000 tokens，
**必然超过 30s**。

**教训**：
1. **合并调用会抬高单次耗时下限**。省的是"次数"，代价是"单次更重"——
   两个维度必须一起看，只盯着省了多少次会漏掉超时。
2. **代码默认值和运行时配置会漂移**。改代码里的默认值对已经在用的配置**无效**，
   必须去改那份存下来的配置。默认值正确 ≠ 运行时正确。
3. fail-open 会把"闸门失灵"伪装成"闸门判定通过"。审计里看到整块 `null`
   要当成**故障**读，不是当成"没问题"。

## Bug 2：对齐闸一直是死的

**现象**：所有格的 `alignmentAudit` 恒为 `null`，看起来像"没有需要对齐的项"。

**日志证据**：`alignment-extract-schema-fail` 累计 **15 次**，
错误是 `items[0]: Expected object, received string`。

**根因**：schema 要求 `{"items":[{"text":"..."}]}`（对象数组），
而模型**稳定返回** `{"items":["..."]}`（纯字符串数组）。
每一次抽取都 zod 失败 → 返回 null → 这一道闸从来没有真正跑过。

**修法**：schema 改成 `z.union([string, {text}])` **同时接受两种形状**，
prompt 也改成模型自然会给的简单形式。

**教训**：
1. **"稳定地返回错"比"偶尔返回错"更危险**。偶尔错会被重试兜住；
   稳定错意味着这条路径 100% 失效，但因为 fail-open 而从不报警。
2. **测试要按模型"实际会给什么"写，不是按 prompt"要求它给什么"写**。
   prompt 是期望，模型的实际输出才是契约。
3. 见 [[panel-gate-fusion]] 里的同类问题：解析器要能吃下已知的几种畸形形态，
   但不能因此放宽成"什么都算对"。

## 两个 bug 的共同点

都是**静默**的：
- 一个被 fail-open 伪装成"通过"
- 一个被 fail-open 伪装成"无需检查"

fail-open 是对的（审核失败不该让用户拿不到图），但它必须有**配对的 fail-loud**：
解析不出来要 `warn`，块级全空要有醒目日志，审计里出现整块 `null` 要能被当成信号读。
